# Личные принципы

Версия протокола обратной связи: **0.3.1**. Версия структуры листа: **0.4**. Точное имя листа: **Принципы**. Таблица: **PersonalPrinciples**.
Машинная спецификация: [schemas/principles.json](../schemas/principles.json).

| Колонка | Название | Ключ | Смысл |
| --- | --- | --- | --- |
| A | Принципы | `principle_text` | Текст личного принципа как буквальное значение, с сохранением условий и области действия. |
| B | Владелец | `owner` | Человек, которому принадлежит этот принцип и к чьему учёту он применяется. |

| C | Дата | `date` | Дата фиксации принципа или убеждения; числовая дата Google Sheets. Неизвестные прежние даты остаются пустыми. |
| D | Убеждение | `belief` | Личная установка владельца; не подтверждение баланса или гарантированного будущего дохода. |
| E | Пример | `example` | Иллюстрация применения; сама по себе не означает совершённого действия. |
| F | ID принципа | `principle_id` | Стабильный ID новых принципов для связи с журналом; прежние строки могут оставаться без ID. |
| G | ID исходника | `source_record_id` | ID буквального источника во «Входящих». |

Колонки A:B сохранены на прежних местах. C:G добавляются справа, без переноса и переписывания старых принципов. Название A «Принципы» остаётся совместимым с прежними читателями; отдельная формулировка убеждения хранится в D.

Одна строка — один принцип конкретного владельца. Несколько принципов допускаются в отдельных строках. Обе колонки обязательны для применимого принципа. При неизвестном владельце обработчик не распространяет правило на всех людей.

Это личные правила, а не общие требования для любых источников. Владелец принципа может отличаться от управляющего системой, автора источника и владельцев ресурсов. Не смешивать эти роли. Реальные принципы и имена находятся только в частной таблице.

## Применение

1. Прочитать лист и определить владельца относящегося к событию принципа по явно известным сведениям; не угадывать личность.
2. Проверить, подходит ли тема и область действия принципа. При конфликте или неопределённости запросить уточнение и сохранить причину в частной базе.
3. Сохранять любые исходные данные во «Входящих» даже при недостатке требуемых личным принципом деталей.
4. При обработке извлекать только сообщённые время, место, количество и другие сведения. Время события отличается от времени получения и записи; место события отличается от места хранения.
5. Если виден конфликт данных с применимым личным принципом или отсутствует требуемое сведение, обязательно сформировать замечание по [правилам обратной связи](principle-feedback.md) и сообщить человеку через Work, ведущий приём. Одного внутреннего статуса недостаточно. Не подставлять текущее время, адрес управляющего, место магазина или иной ресурсный адрес за неизвестные время и место события.
6. Сохранить связь применённого правила с предметным результатом в частной базе. Чтение принципа не разрешает новые внешние действия и не меняет протокол доступа.

Лист читается другими Work в пределах разрешённого доступа. Добавление или изменение принципов выполняется по явному поручению их владельца или уполномоченного лица; обычный приём данных не даёт права редактировать этот лист. Версия 0.4 добавляет дату, убеждение, пример, стабильный ID новых принципов и связь с исходником. Автоматическое исполнение и полная история правок не реализованы.

## Ссылка на принцип в замечании

Для совместимости номер принципа — порядковый номер непустой строки **среди принципов данного владельца** при чтении сверху вниз, начиная с 1. Заголовок и строки других владельцев не учитываются. Номер не является постоянным ID и может измениться при сортировке или вставке строк.

Поэтому замечание обязательно сохраняет владельца, номер на момент проверки, точный текст принципа и частный диапазон исходной строки. После правки листа обработчик повторно читает принципы; не связывает старое замечание с новым правилом только по совпавшему номеру. При наличии ID принципа сохранять его дополнительно; для прежних строк без ID продолжает действовать ссылка на владельца, точный текст и диапазон. Полная история изменений остаётся будущим расширением.

## Примеры и осознанное применение

Лист **Применение принципов**, нативная таблица **PrinciplePractice**, версия **1.0**. Машинное описание находится в `practice_journal` файла [schemas/principles.json](../schemas/principles.json).

| Колонка | Название | Смысл |
| --- | --- | --- |
| A | Дата | Дата внесения примера; не подставлять её за неизвестную дату события. |
| B | ID принципа | Стабильная ссылка на F листа «Принципы». |
| C | Пример | Ситуация и её контекст. |
| D | Статус | «Разбор», «Намерение» или «Применено». |
| E | Осознанно | «Не подтверждено», «Да» или «Нет». |
| F | Фактическое действие | Только действительно сообщённое действие; желаемый ответ не считать сказанным. |
| G | Результат | Только известный результат; неизвестное оставить пустым или явно отметить отсутствие сведений. |
| H | ID исходника | ID первичного сообщения во «Входящих». |

Новые примеры добавлять отдельными связанными строками; старые не затирать и не объединять в одну растущую ячейку. «Применено» требует сообщения о фактическом действии. «Осознанно: Да» требует явного подтверждения владельца, что в тот момент он осознанно следовал принципу. Отсутствие такого сообщения означает «Не подтверждено», а не «Нет». Разбор, намерение, действие и финансовый перевод — разные события.

Личное убеждение о деньгах не является доказательством наличия денег или гарантией будущих поступлений. При финансовом учёте сохраняются требования к фактам и применимые принципы владельца. При видимом неразрешённом противоречии использовать действующий протокол обратной связи, не отменяя молча прежний принцип.

## Миграция 0.3 → 0.4

1. По метаданным и живому чтению проверить A:B, прежние строки, нативную таблицу и свободные целевые диапазоны.
2. Добавить C:G справа; расширить существующую PersonalPrinciples на новые колонки и фактически добавленные строки. Старые значения, владельцев, примечания и порядок сохранить. Исторические даты и ID не заполнять догадками.
3. Создать «Применение принципов» по схеме выше; подтвердить отсутствие одноимённого листа, прежде чем создавать его. При повторной попытке сначала читать уже созданные данные.
4. По прямому поручению владельца сохранить буквальный запрос во «Входящие», добавить принцип/убеждение и пример с корректным статусом. Сохранить связь с исходником.
5. Перечитать записанные диапазоны и проверить сохранность прежних A:B, таблицы, даты и допустимые статусы.

Это ручной протокол. Документация и журнал не запускают фоновое обнаружение применений, напоминания или автоматическую запись из других чатов.
